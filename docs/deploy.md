# AgencySignal — deploying

How this repository becomes a running site. Read the README first for what the
system does and how to run it locally.

## Where it deploys

One Cloudflare Worker, hosted by the OpenAI Sites runtime. `.openai/hosting.json`
names the project and declares the only two bindings the app has:

```json
{ "d1": "DB", "project_id": "appgprj_6a83ce5830fc8191bb022a6a96cfc634", "r2": "BUCKET" }
```

There is deliberately no `wrangler.toml` and no `deploy` script. The runtime
supplies both bindings and applies the migrations packaged into
`dist/.openai/drizzle`, so the deploy is triggered from the app environment that
owns that project id, not from this repository. `dist/server/wrangler.json` is
generated by the build for local Miniflare and carries a placeholder
`database_id`; it is not the hosted configuration.

## Preflight

Run all four. Each is a gate, and `build` refuses to hand off an artifact that
would fail on the runtime.

```bash
npm run install:ci        # locked, integrity-checked install
npm run build             # bounded vinext build, then validate-artifact.sh
npm test                  # the build plus the full suite
npm run lint
```

| Command | What a pass looks like |
| --- | --- |
| `install:ci` | `npm ci passed and vinext is available` |
| `build` | `Validated Sites artifact: ESM Worker default.fetch and hosting manifest are present.` |
| `test` | `# fail 0` |
| `lint` | **4 errors expected.** React effect patterns in `dashboard.tsx` and `prospect-detail.tsx`, recorded in the handover. Lint is not part of the build gate. Any error outside those two files is new and worth reading. |

A green `build` leaves a complete artifact:

```text
dist/server/index.js        the Worker, ESM, default export with fetch()
dist/.openai/hosting.json   the bindings manifest
dist/.openai/drizzle/       every migration, plus meta/_journal.json
dist/client/                static assets
```

If `dist/server/index.js` or `dist/.openai/hosting.json` is missing,
`validate-artifact.sh` exits 66 and the artifact must not be deployed.

## Credentials

Generate them locally. `--print-only` skips writing `.dev.vars`; drop the flag to
set up local development at the same time. Either way the script prints the four
generated sign-in secrets ready to paste — the API keys it does not print back,
because you supplied them.

```bash
npm run auth:credentials -- --print-only \
  --email you@example.com --password 'a long passphrase' \
  --owner 'Your Name' --pagespeed-key KEY --places-key KEY
```

The password itself is never stored. Re-run the script to rotate.

### Sign-in — all four, or the app is unusable

| Secret | Without it |
| --- | --- |
| `AGENCYSIGNAL_LOGIN_EMAIL` | Login always fails; every page and API returns 401. |
| `AGENCYSIGNAL_PASSWORD_SALT` | Same. |
| `AGENCYSIGNAL_PASSWORD_HASH` | Same. |
| `AGENCYSIGNAL_SESSION_SECRET` | Same. Rotating it signs out every existing session. |

### Audit

| Secret | Without it |
| --- | --- |
| `PAGESPEED_API_KEY` | PageSpeed applies its unkeyed quota and returns 429 in a batch; those checks report as not measured. Free. |
| `GOOGLE_PLACES_API_KEY` | The profile cannot be read, so the service-line gap table — the point of the tool — stays empty. Billed per request. |

### Optional

`OPENAI_API_KEY` and `OPENAI_MODEL` (rationale prose; composed deterministically
without them), and `AGENCYSIGNAL_OWNER_NAME` (the name on prospect-facing
reports; falls back to one derived from the login address).

A missing optional key never fails a run. A missing audit key lowers what the run
covers, and the run says which checks it could not measure and why.

## Migrations

The runtime applies `dist/.openai/drizzle` on deploy, tracked by tag, so an
already-applied migration is skipped and a redeploy is safe to repeat.

Two of them mutate data rather than schema. On a first deploy against a database
that already holds real prospect data, both will run:

- `0011_invalidate_pregate_runs.sql` nulls the scores of runs finalised before
  the confidence gate existed, and clears the headline score on leads where the
  engine is the only thing that could have written it.
- `0014_retire_legacy_scores.sql` clears every `score_source = 'legacy'` score,
  which the retired `/api/audit` path produced under a different rubric.

Both are intentional: a score with no recorded provenance is worse than no score.
Look at the database before the first deploy anyway.

## Verify the deploy

1. Sign in with the email and password used to generate the secrets. A 401 here
   means one of the four sign-in secrets is missing or mistyped.
2. Add one business, name and website.
3. Press **Run website audit** and tick it through. The run advances one module
   per request and resumes from any later tick, so a closed tab loses nothing.
4. Check the crawl diagnostics on the finished run — final status, robots.txt
   fetchability, pages reached against pages attempted.
5. Build the package and open the report, proposal and mockup at their public
   tokens.

## What the first real runs are for

Two figures in this system have never been exercised against a real prospect,
and the deployed environment is the only place they can be:

- **Blocking rate is unmeasured.** The crawler has never run against real
  small-business sites from the hosted runtime. Wix and Squarespace builds,
  JS-rendered navigation, and Cloudflare or Sucuri bot protection are the
  untested cases. Every run records the diagnostics that answer this.
- **The confidence threshold is a placeholder.** 60% has only ever been
  exercised with PageSpeed absent. Re-tune it in
  `lib/audit/scoring-config.js` against real runs.

Treat the first five audits as calibration, not output.
