# AgencySignal — deploying

How this repository becomes a running site. Read the README first for what the
system does and how to run it locally.

## Where it deploys

One Cloudflare Worker, hosted by the OpenAI Sites runtime. `.openai/hosting.json`
names the project and declares the only two bindings the app has:

```json
{ "d1": "DB", "project_id": "appgprj_6a83ce5830fc8191bb022a6a96cfc634", "r2": "BUCKET" }
```

There is no `wrangler.toml`, and the Sites deploy needs none: the runtime
supplies both bindings and applies the migrations packaged into
`dist/.openai/drizzle`, so that deploy is triggered from the app environment
owning the project id, not from this repository. `dist/server/wrangler.json` is
generated by the build for local Miniflare and carries a placeholder
`database_id`; it is not the hosted configuration.

If that project no longer exists, the id above is dead and the Sites path ends
here. Deploy to your own Cloudflare account instead — see below.

## Two ways to deploy

**The Sites runtime**, described above and in the rest of this document. It
supplies both bindings and applies the migrations itself.

**Your own Cloudflare account**, described in this section. Nothing supplies the
bindings and nothing applies the migrations, so both are steps you run. Use this
when the Sites project is gone, or when you want the deployment to be yours.

Only one of the two bindings is actually required. `DB` is — `db/index.ts`
throws without it. `BUCKET` is optional: every call site in `lib/audit-screenshots.ts`
is guarded, so a deploy without R2 works and simply stores no audit screenshots.
That matters because D1 and Workers both have a free tier and R2 asks for a
payment method, so the first deploy needs neither.

### Deploying to Cloudflare

Two commands.

```bash
npx wrangler login          # once, opens a browser
npm run setup:cloudflare
```

`setup:cloudflare` finds or creates the D1 database, builds, applies the
migrations, generates a dashboard login if there is not one already, deploys,
and uploads the secrets as part of that deploy. It prints the site URL and, on a
first run, the generated password.

It is safe to re-run. The database is reused rather than recreated, migrations
are tracked by tag, and an existing login in `.dev.vars` is kept — a second run
will not silently rotate your password and sign you out.

```
--email=you@example.com   used when generating a first login; prompts when a terminal is attached
--name=my-worker          Worker and database name, default agency-signal
--r2=my-bucket            attach an R2 bucket; omitted entirely by default
--skip-build              reuse the existing dist/ instead of rebuilding
--pagespeed-key=KEY       audit key, stored and uploaded with the deploy
--places-key=KEY          audit key, stored and uploaded with the deploy
```

It asks for the two audit keys before deploying, so they upload with the same
secrets file as the login. Both are optional — leave either blank and the deploy
proceeds, saying which checks will report as not measured. A key already in
`.dev.vars` is reused without asking. Pass them directly to skip the prompts:

```bash
npm run setup:cloudflare -- --pagespeed-key=KEY --places-key=KEY
```

Adding one after the fact takes a redeploy or a secret put:

```bash
npx wrangler secret put PAGESPEED_API_KEY     --name agency-signal
npx wrangler secret put GOOGLE_PLACES_API_KEY --name agency-signal
```

### Doing it by hand

The same sequence, if you want to run the pieces yourself or something in the
middle failed:

```bash
npx wrangler login
npx wrangler d1 create agency-signal          # prints database_id
export CLOUDFLARE_D1_DATABASE_ID=<the id it printed>

npm run build
npm run db:migrate:remote                     # schema first, or the Worker 500s
npm run deploy
```

Then the secrets, which are per-Worker and so can only be set once that first
deploy has created it:

```bash
npx wrangler secret put AGENCYSIGNAL_LOGIN_EMAIL    --name agency-signal
npx wrangler secret put AGENCYSIGNAL_PASSWORD_SALT  --name agency-signal
npx wrangler secret put AGENCYSIGNAL_PASSWORD_HASH  --name agency-signal
npx wrangler secret put AGENCYSIGNAL_SESSION_SECRET --name agency-signal
```

**Between that deploy and the last of those, every request returns 401.** That is
the intended failure: `app/dashboard-auth.ts` has no credentials to compare
against, so it refuses everyone rather than admitting anyone. Secrets take effect
without a redeploy, so the app starts working as soon as the fourth one lands.
`npm run setup:cloudflare` avoids the window entirely by uploading the secrets
with the deploy.

`npm run deploy` and `npm run db:migrate:remote` deliberately do **not** run
through `scripts/sites-env.sh`, unlike every other command here. That helper
redirects `XDG_CONFIG_HOME` into `.sites-runtime`, which is where Wrangler keeps
its OAuth token — routing them through it would hide a perfectly good
`wrangler login` and report you as unauthenticated on every deploy.

### What the deploy script does

`scripts/deploy-cloudflare.mjs` patches the Wrangler config the build already
emits at `dist/server/wrangler.json`, rather than keeping a second hand-written
config that could drift from what the build produces. It replaces the local
development bindings — a placeholder D1 id and a Miniflare-only bucket — with the
real ones, names the `ASSETS` binding that `worker/index.ts` reads, and omits the
R2 binding entirely unless `CLOUDFLARE_R2_BUCKET` is set.

| Variable | |
| --- | --- |
| `CLOUDFLARE_D1_DATABASE_ID` | Required. Refuses to deploy without it, because a Worker bound to a database that does not exist 500s on every page. |
| `CLOUDFLARE_WORKER_NAME` | Defaults to `agency-signal`. |
| `CLOUDFLARE_D1_DATABASE_NAME` | Defaults to the Worker name. |
| `CLOUDFLARE_R2_BUCKET` | Optional. Without it, no R2 binding is shipped. |

`npm run deploy -- --dry-run` writes the patched config and stops, so you can read
what would be deployed before deploying it.

### Migrations on Cloudflare

The Sites runtime applies `dist/.openai/drizzle` on deploy. **A direct
`wrangler deploy` does not.** `npm run db:migrate:remote` is the same runner as
the local `npm run db:migrate`, pointed at the deployed database; it tracks
applied migrations by tag in `_agencysignal_migrations`, so it is safe to re-run
and applies only what is pending.

Run it before `npm run deploy`, not after. A Worker serving traffic against a
database without its schema returns 500 on every page that touches data.

## Running the commands here

Any Unix shell with Node 22.13 or newer. The scripts resolve the GNU tools they
need through `scripts/portable-tools.sh`, so macOS works without Homebrew:
`shasum` stands in for `sha256sum`, a `mkdir` lock stands in for `flock`, and a
missing GNU `timeout` drops the time bound with a warning rather than failing.
Installing coreutils (`brew install coreutils`) restores the bound.

Windows needs WSL.

## Preflight

Run all four. Each is a gate, and `build` refuses to hand off an artifact that
would fail on the runtime.

```bash
npm run install:ci        # locked, integrity-checked install
npm run build             # bounded vinext build, then validate-artifact.sh
npm test                  # the build plus the full suite
npm run lint
```

| Command | What a pass looks like |
| --- | --- |
| `install:ci` | `npm ci passed and vinext is available` |
| `build` | `Validated Sites artifact: ESM Worker default.fetch and hosting manifest are present.` |
| `test` | `# fail 0` |
| `lint` | **4 errors expected.** React effect patterns in `dashboard.tsx` and `prospect-detail.tsx`, recorded in the handover. Lint is not part of the build gate. Any error outside those two files is new and worth reading. |

A green `build` leaves a complete artifact:

```text
dist/server/index.js        the Worker, ESM, default export with fetch()
dist/.openai/hosting.json   the bindings manifest
dist/.openai/drizzle/       every migration, plus meta/_journal.json
dist/client/                static assets
```

If `dist/server/index.js` or `dist/.openai/hosting.json` is missing,
`validate-artifact.sh` exits 66 and the artifact must not be deployed.

## Credentials

Generate them locally. `--print-only` skips writing `.dev.vars`; drop the flag to
set up local development at the same time. Either way the script prints the four
generated sign-in secrets ready to paste — the API keys it does not print back,
because you supplied them.

```bash
npm run auth:credentials -- --print-only \
  --email you@example.com --password 'a long passphrase' \
  --owner 'Your Name' --pagespeed-key KEY --places-key KEY
```

The password itself is never stored. Re-run the script to rotate.

### Sign-in — all four, or the app is unusable

| Secret | Without it |
| --- | --- |
| `AGENCYSIGNAL_LOGIN_EMAIL` | Login always fails; every page and API returns 401. |
| `AGENCYSIGNAL_PASSWORD_SALT` | Same. |
| `AGENCYSIGNAL_PASSWORD_HASH` | Same. |
| `AGENCYSIGNAL_SESSION_SECRET` | Same. Rotating it signs out every existing session. |

### Audit

| Secret | Without it |
| --- | --- |
| `PAGESPEED_API_KEY` | PageSpeed applies its unkeyed quota and returns 429 in a batch; those checks report as not measured. Free. |
| `GOOGLE_PLACES_API_KEY` | The profile cannot be read, so the service-line gap table — the point of the tool — stays empty. Billed per request. |

### Optional

`OPENAI_API_KEY` and `OPENAI_MODEL` (rationale prose; composed deterministically
without them), and `AGENCYSIGNAL_OWNER_NAME` (the name on prospect-facing
reports; falls back to one derived from the login address).

A missing optional key never fails a run. A missing audit key lowers what the run
covers, and the run says which checks it could not measure and why.

## Migrations

The runtime applies `dist/.openai/drizzle` on deploy, tracked by tag, so an
already-applied migration is skipped and a redeploy is safe to repeat.

Two of them mutate data rather than schema. On a first deploy against a database
that already holds real prospect data, both will run:

- `0011_invalidate_pregate_runs.sql` nulls the scores of runs finalised before
  the confidence gate existed, and clears the headline score on leads where the
  engine is the only thing that could have written it.
- `0014_retire_legacy_scores.sql` clears every `score_source = 'legacy'` score,
  which the retired `/api/audit` path produced under a different rubric.

Both are intentional: a score with no recorded provenance is worse than no score.
Look at the database before the first deploy anyway.

## Verify the deploy

1. Sign in with the email and password used to generate the secrets. A 401 here
   means one of the four sign-in secrets is missing or mistyped.
2. Add one business, name and website.
3. Press **Run website audit** and tick it through. The run advances one module
   per request and resumes from any later tick, so a closed tab loses nothing.
4. Check the crawl diagnostics on the finished run — final status, robots.txt
   fetchability, pages reached against pages attempted.
5. Build the package and open the report, proposal and mockup at their public
   tokens.

## What the first real runs are for

Two figures in this system have never been exercised against a real prospect,
and the deployed environment is the only place they can be:

- **Blocking rate is unmeasured.** The crawler has never run against real
  small-business sites from the hosted runtime. Wix and Squarespace builds,
  JS-rendered navigation, and Cloudflare or Sucuri bot protection are the
  untested cases. Every run records the diagnostics that answer this.
- **The confidence threshold is a placeholder.** 60% has only ever been
  exercised with PageSpeed absent. Re-tune it in
  `lib/audit/scoring-config.js` against real runs.

Treat the first five audits as calibration, not output.
